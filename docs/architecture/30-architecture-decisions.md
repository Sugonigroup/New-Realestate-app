# 30 — Architecture Decision Records

Format: Decision / Context / Options / Rationale / Consequences / Alternatives rejected. ADR-01…07 (modular monolith, RLS tenancy, TS stack, Tally boundary, in-house workflow engine, Redis Streams, WhatsApp-first) are recorded in `../../02 §2 Key ADRs` and remain **in force**; they are summarized here and extended with AI-era decisions. All technology choices are consistent with the repository's documented stack (`02-current-state-analysis §2`) — nothing new is introduced without a compatible embedding.

## ADR-AI1 — AI layer as contexts in the existing modular monolith (worker-separated)
**Decision:** implement the AI operating layer as new bounded contexts (`ai_*`, `knowledge`, `reporting`) inside the Core API, executing in separate `ai-workers` processes from the same image. **Context:** 12 agents + RAG + reporting must not destabilize money-path ERP; team size small; repo stack is NestJS monolith (ADR-01). **Options:** (a) same monolith + workers, (b) separate AI microservice + own DB, (c) serverless functions per agent. **Rationale:** reuse runtime/observability/CI; event-driven isolation via queues gives the operational separation without distributed-systems cost; extraction path exists if an agent class needs independent scale. **Consequences:** shared failure domain mitigated by queue bulkheads and worker separation; memory limits tuned per worker class. **Rejected:** (b) premature distributed ops; (c) long-running agent loops and DB-affine tools don't fit function economics.

## ADR-AI2 — One unified approval engine for human and AI actions
**Decision:** AI L4 requests become rows in the existing `approval_requests` (`source=ai_agent`) executed by the human approval engine from `../../09`. **Context:** two approval paths would fork audit and UX. **Options:** (a) unified, (b) parallel AI-approval store, (c) auto-execute under confidence threshold. **Rationale:** single inbox/audit/SoD; human pathways unchanged; confidence-threshold auto-execution is explicitly banned for L4 classes. **Consequences:** approval card extended with evidence/confidence; analytics distinguish sources. **Rejected:** (b) audit fragmentation; (c) violates the critical human-approval rule.

## ADR-AI3 — Policy-as-data autonomy engine (not in-code rules)
**Decision:** autonomy matrix (10) is versioned tenant-editable data evaluated by a dedicated Policy Engine on every tool call. **Context:** autonomy must evolve per tenant/regulator without deploys; must be auditable. **Options:** (a) policy-as-data + engine, (b) hardcoded per-agent gates, (c) LLM self-judges. **Rationale:** governance reviews and tightening are config changes; engine is unit-testable pure logic; LLM self-judgment for authorization is never acceptable. **Consequences:** schema versioning; negative tests per matrix row. **Rejected:** (b) redeploy per policy change; (c) security outside the model is a binding principle.

## ADR-AI4 — pgvector on PostgreSQL for RAG (no vector DB now)
**Decision:** embeddings + hybrid retrieval on the existing Postgres (HNSW). **Context:** scale envelope ≤10M chunks/50 tenants; stack reuse mandate. **Options:** (a) pgvector, (b) dedicated vector DB (Pinecone/Qdrant/Milvus), (c) Elasticsearch. **Rationale:** one less stateful system; RLS joins are native (permission-filtered retrieval is a SQL predicate — a security feature); scale-out trigger and `RetrievalPort` abstraction documented (15 §7). **Consequences:** instance memory sizing for HNSW; re-index procedure on embedding-model change. **Rejected:** (b)/(c) premature infra + a second security boundary to enforce.

## ADR-AI5 — Deterministic-first agents (LLM at classification/explanation edges)
**Decision:** every agent computes facts in domain code (EVM, cover days, 3-way match); LLM only classifies/explains/recommends over those facts, outputs JSON-validated. **Context:** binding principles 6; audit defensibility; India financial compliance. **Options:** (a) deterministic-first, (b) LLM-agentic calculation, (c) hybrid without validators. **Rationale:** money/date correctness and replayability; cheaper models viable. **Consequences:** agents need rich read tools; LLM failures degrade gracefully to deterministic insights. **Rejected:** (b)/(c) unacceptable for financial truth.

## ADR-AI6 — REST + SSE, no GraphQL
**Decision:** keep REST/OpenAPI + SSE for AI streams. **Context:** clients are first-party; contract-first tooling already specified. **Options:** REST+SSE vs GraphQL federation. **Rationale:** caching, authz per-endpoint simplicity, codegen already planned. **Consequences:** composite BFF endpoints for heavy screens. **Rejected:** GraphQL overhead without a third-party consumer base.

## ADR-AI7 — Agent outputs land as drafts/queues, never direct postings for sensitive domains
**Decision:** NCRs, PRs, inspections, demand corrections created by agents are drafts routed to human confirmation queues; extraction results never post to finance directly. **Context:** trust ramp; statutory exposure. **Options:** (a) draft-first everywhere sensitive, (b) direct post with high confidence. **Rationale:** measurable adoption path to autonomy; regulators/auditors see human checkpoints. **Consequences:** queue UX load — mitigated by batch confirm. **Rejected:** (b) trust not yet earned; revisit only with eval evidence per `27` Phase 8 gates.

## ADR-AI8 — Cost governance at the gateway
**Decision:** all LLM traffic via one gateway module enforcing routing, masking, budgets, caching, per-run cost accounting. **Context:** multi-tenant SaaS; unpredictable model tariffs. **Options:** (a) gateway, (b) direct SDK calls per agent. **Rationale:** one enforcement point for security (masking), finance (budgets), ops (failover) — `28`. **Consequences:** gateway is critical infra — versioned, tested, observable. **Rejected:** (b) unmanageable cost/security sprawl.
